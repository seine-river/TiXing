## 1. 产品概述

### 1.1 产品定位
面向小学生（及协同的家长/老师）的智能错题记录与科学复习工具，核心价值是"拍照即记录，系统助复习"。

### 1.2 目标用户与角色
| 角色 | 说明 |
|---|---|
| 学生（Student） | 主用户，小学 3-6 年级，识字量与操作能力有限，交互需大按钮、少输入（尤其少打字）、强引导 |
| 家长（Parent） | 协同角色，负责设置提醒、查看报告、复核系统判定、管理隐私/消费权限，如需付费由家长身份完成 |
| 老师（Teacher） | 可选扩展角色，班级/学科视角，非首期必需 |
| 内部运营/产品/技术/合规人员 | 通过独立的管理后台查看聚合运营数据，不接触具体孩子的原始内容（见3.12） |

### 1.3 核心价值与场景
1. 做完练习/试卷后，家长或孩子拍照（或从相册选取已有照片），圈出错题，系统识别并归档
2. 系统按遗忘曲线定期推送复习提醒
3. 复习时以"重做一遍"的方式检验是否真正掌握，掌握与否由系统客观判定
4. 系统汇总薄弱知识点，输出可执行的复习策略和阶段报告
5. 结合年级、教材版本，孩子可在匿名、安全的错题社区中浏览同龄人的典型错题
6. 社区聚合数据反哺家长端的付费深度学情报告（详见第11节）
7. 内部团队通过运营后台掌握整体项目运营情况，支撑产品与商业决策（详见3.12）

### 1.4 术语表
| 术语 | 定义 |
|---|---|
| 错题（Mistake） | 一条被系统记录的错题实体，含原图、识别文本、学科、知识点标签、复习记录等 |
| 掌握判定（Mastery Evaluation） | 系统基于正确率+反应速度+跨时间验证自动判断某道错题是否已被真正掌握的机制，不依赖用户手动标记 |
| 识别确认（OCR Confirmation） | 拍照识别后，用户必须核对/修正识别结果才能保存的强制环节 |
| 间隔重复（Spaced Repetition） | 按递增时间间隔安排复习的排期算法 |
| 知识点画像（Knowledge Profile） | 某学生在某知识点上的聚合统计（错题数、掌握度、趋势） |
| 社区聚合数据（Community Aggregate Data） | 经脱敏、审核后的多学生错题数据聚合成的"易错知识点"统计信号 |
| 运营后台（Ops/BI Console） | 面向内部团队的独立管理系统，用于查看脱敏后的整体项目运营数据，与C端App分离 |
| 核心逻辑服务端化 | 将掌握判定、间隔重复排期等对结果一致性要求高的算法实现为后端统一服务，供所有客户端平台调用，而非各端各自实现 |

## 2. 范围与迭代规划

| 阶段 | 范围（Must） | 明确不包含 |
|---|---|---|
| 第一阶段 MVP | 拍照/相册录题、强制识别确认（低输入优先）、基础错题本、间隔重复提醒、复习模式（客观题自动判分+主观题自评，低输入作答方式）、掌握判定基础规则版（阈值用经验值）、**基础运营看板**（留存、使用频次、识别成功率等核心指标） | 错题社区、积分商城、订阅报告、完整版BI、多学科（先数学/语文）、Android/iOS/桌面端 |

| 第三阶段 | 家长端深度协同（复核界面）、掌握判定阈值的数据校准、积分与成长体系（非货币） | 社区、订阅、跨端 |
| 第四阶段 | 错题社区（先灰度测试脱敏与审核机制） | 订阅商业化、跨端 |
| 第五阶段 | 家长端订阅深度报告（商业化，见第11节）、**完整版运营BI**（商业化/内容/技术健康度全维度看板） | 跨端 |
| 第六阶段（视产品验证结果决定） | 跨端评估与推进（Android/iOS优先，桌面Windows/macOS其次），详见5.5节 | — |

> 社区、订阅、跨端三个方向均建议独立评估上线时机，不与前序功能强耦合排期。跨端启动前，建议先在 HarmonyOS 单端验证核心指标（留存、复习完成率、掌握判定准确性），详见5.5节"关于是否现在就做跨端的建议"。

## 3. 功能需求规格

### 3.1 拍照录题（FR-CAP）
- **FR-CAP-01**：支持"拍照"与"从相册选取已有照片"两个平级入口
- **FR-CAP-02**：拍照/选图后进行质量检测（模糊度、倾斜角、光照），不达标时提示具体原因并允许重拍或换图
- **FR-CAP-03**：图像自动裁边矫正（去畸变、增强对比度）
- **FR-CAP-04**：支持手指框选/涂抹圈选题目区域，支持同一页多题连续圈选，支持撤销
- **FR-CAP-05**：原始图片必须以高清原图形式永久保存，作为该错题的"事实来源"，不因识别结果而被裁剪或替换

### 3.2 识别与准确率保障（FR-OCR）
- **FR-OCR-01**：印刷体文字走通用OCR引擎；数学公式/图形走专门识别通道；每个识别字段返回置信度分值
- **FR-OCR-02**：低置信度内容在UI上必须有可见的高亮标记（如波浪线）
- **FR-OCR-03**：识别完成后进入"识别确认页"，用户逐项核对/修正后才能保存；未完成核对不可保存
- **FR-OCR-04**：修正方式按"减少打字"优先级依次提供：① 若OCR能给出候选项，优先做候选词点选替换（零打字）；② 语音说出正确内容转文字；③ 手写输入板（手指/触控笔直接书写，系统识别为文字，比标准拼音键盘更符合小学生书写习惯）；④ 仅当以上都不适用时才回退到标准键盘打字，且需提供输入联想/常见词候选降低击键量
- **FR-OCR-05**：整体识别失败时，允许仅保存原图、后续再补充文字，不阻塞录入流程
- **FR-OCR-06**：（可选，需评估调用成本）低置信度手写内容可路由至多模态大模型做"第二意见"，但其输出同样需经过FR-OCR-03的强制核对，不可绕过

### 3.3 错题管理（FR-MNG）
- **FR-MNG-01**：错题卡片展示：题目图片/文字、学科、知识点标签、错误类型（可选打标）、录入时间、复习次数、掌握状态
- **FR-MNG-02**：支持按学科/知识点/错误类型/时间/掌握状态分类浏览与搜索
- **FR-MNG-03**：支持补充"讲解笔记"，输入方式优先级：语音转文字 > 直接拍摄一张手写讲解/老师批注的照片作为笔记附件（不要求转成文字）> 键盘打字（兜底选项）
- **FR-MNG-04**：掌握状态字段（status）仅可由系统的掌握判定算法（见6.4）写入，客户端不提供"一键标记已掌握"的直接写入接口；家长可发起"复核申诉"（见3.6）

### 3.4 复习与自动掌握判定（FR-REV）
- **FR-REV-01**：作答方式按题型区分输入手段，均以减少打字为原则：选择/判断题 → 点选；数字类填空/计算题 → 数字键盘（非全键盘）；文字类填空题（语文/英语）→ 手写输入板为主、辅以语音输入，不要求孩子用拼音/字母键盘逐字打字；系统对客观题直接比对标准答案判分
- **FR-REV-02**：主观题（简答/造句/作文类）作答后展示参考答案，学生自评一致与否；自评结果标记为低权重判分方式，不单独作为掌握判定依据
- **FR-REV-03**：每次复习记录：是否正确、作答用时、判分方式
- **FR-REV-04**：掌握判定按6.4节算法自动执行，判定结果实时更新错题的status与知识点画像
- **FR-REV-05**：复习完成页展示本次正确率、进步反馈、本次获得积分，语言以正向鼓励为主

### 3.5 复习提醒与策略（FR-REM）
- **FR-REM-01**：基于间隔重复算法（见6.3）自动生成"今日待复习"清单，题量可配置上限（默认5-10题）
- **FR-REM-02**：复习策略：错误率高的知识点优先、同类型题目打包复习、按家长设置的可用时间段智能排布
- **FR-REM-03**：提醒渠道为应用内+系统通知，家长可设置免打扰时段

### 3.6 家长协同（FR-PAR）
- **FR-PAR-01**：家长可查看孩子的错题本、报告、掌握判定依据（正确率曲线、用时曲线）
- **FR-PAR-02**：家长可代为拍照录入、调整提醒设置
- **FR-PAR-03**：家长可对某条掌握判定结果发起"复核申诉"，需填写简单理由；复核不是无条件覆盖，建议记录申诉历史供后续算法调优参考
- **FR-PAR-04**：家长收到"连续多次未复习""某知识点持续薄弱"等提醒

### 3.7 数据导出与导入（FR-DATA）
- **FR-DATA-01**：导出格式支持 PDF（保留原图排版的打印版）与结构化数据文件（JSON）
- **FR-DATA-02**：导出支持按学科/知识点/时间范围/掌握状态筛选
- **FR-DATA-03**：导入支持本应用备份文件（换机场景）与常见表格文件（Excel/CSV，供教师/家长批量导入）
- **FR-DATA-04**：导入的题目必须复用 FR-OCR-03 的识别确认流程，不因来源是"导入"而跳过核对

### 3.8 用户与学习档案（FR-PROF）
- **FR-PROF-01**：引导流程采集，全部采用选择而非自由输入：年级（必填，选择器）、教材版本（必填，选择器）、地区（选填，省市联动选择器，非文字输入）、学校（选填，搜索式选择列表，允许模糊搜索但不要求完整打字校名，列表无匹配可直接跳过，不强制补全）
- **FR-PROF-02**：地区、学校字段默认不对外可见，仅在用户主动开启对应社区可见性选项后生效
- **FR-PROF-03**：档案信息用于匹配知识点体系、生成同年级对比基准值

### 3.9 错题社区（FR-COM）
- **FR-COM-01**：内容以"学科→年级→知识点"分层组织，非用户主页/社交关系链模式
- **FR-COM-02**：孩子的社区浏览/分享权限默认关闭，需家长在FR-PROF所在设置页主动开启，两权限相互独立
- **FR-COM-03**：分享前系统自动检测并遮盖原图中的姓名、学号等可识别信息，脱敏后需家长二次确认，确认后内容进入审核队列
- **FR-COM-04**：审核采用自动过滤（敏感词/违规图像检测）+人工复核结合，通过后方可公开展示
- **FR-COM-05**：互动方式仅限点赞、收藏、"加入我的错题本"，不提供私信、加好友、评论区等可暴露联系方式的功能（同时也是本文"减少打字"原则的延伸——不设自由文本评论区）
- **FR-COM-06**：聚合的"易错知识点"统计信息，仅在样本量达到最小阈值（见6.5）后展示，未达标显示"数据积累中"

### 3.10 积分与激励（FR-PTS）
- **FR-PTS-01**：积分获取行为：录入错题、按时完成今日复习、知识点被判定"已掌握"、连续复习打卡（设上限）、经审核通过的社区贡献（低权重）
- **FR-PTS-02**：积分仅可兑换应用内虚拟内容（封面、成长树造型、称号），**不可充值购买，不构成查看核心学习内容的门槛**
- **FR-PTS-03**：不实现"断签清零"机制（允许合理补签）；不实现限时任务倒计时；排行榜仅展示正向Top名单，不展示末位排名
- **FR-PTS-04**：家长可查看积分明细，可关闭排行榜/社区排名展示

### 3.11 家长端订阅（商业化，FR-SUB，详见第11节）
- **FR-SUB-01**：付费入口仅出现在家长身份验证通过的界面，孩子账号内不出现任何支付相关UI
- **FR-SUB-02**：订阅内容为分层解锁的深度学情报告（同年级对比、历史趋势、错误归因、跨知识点关联、阶段重点提示），基础统计对孩子/家长始终免费
- **FR-SUB-03**：报告中涉及社区对比数据的部分，必须标注样本量来源，样本量不足时不展示对比结论

### 3.12 运营数据与管理后台（FR-OPS）
- **FR-OPS-01**：建设独立的Web管理后台（Admin/BI Console），面向内部运营/产品/技术/合规角色，与C端App完全分离，不面向学生/家长开放
- **FR-OPS-02**：核心运营指标覆盖以下维度：
  - **用户增长**：新增/活跃/留存（DAU/WAU/MAU）、分年级/地区分布
  - **功能使用**：拍照录入频次、识别置信度分布与识别确认通过率、复习完成率、掌握判定通过率与平均判定用时
  - **内容与社区**：社区提交量、审核通过率、举报/驳回率、点赞收藏活跃度
  - **商业化**：订阅转化率、续费率、客单价、单次报告购买量
  - **技术健康度**：接口延迟、崩溃率、OCR调用成功率与耗时、多模态大模型兜底调用量与成本
- **FR-OPS-03**：内部运营人员默认只能看到**聚合/脱敏后**的统计数据，不能直接检索/查看具体某个孩子的错题原图或识别文本内容；如确需排查具体案例（如客诉、审核申诉），需走单独的、有审计日志的"案例查询"权限，区别于日常运营看板权限
- **FR-OPS-04**：支持按角色分配看板权限——运营/产品看增长与内容指标；技术看性能与稳定性指标；合规/法务看未成年人相关操作审计（脱敏记录数、家长确认记录、复核申诉记录）
- **FR-OPS-05**：所有面向内部人员的敏感操作（如访问案例级数据）需记录审计日志，明确操作人、时间、原因

## 4. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 拍照到识别确认页展示的端到端延迟建议控制在2秒以内（端侧OCR路径）；多模态大模型"第二意见"路径允许更高延迟，但需有加载态提示 |
| 隐私合规 | 不采集身份证号等政府身份证件信息；学校/地区选填且默认不公开；社区分享前必须脱敏；未成年人账号不出现支付入口；内部运营数据默认脱敏聚合（见3.12） |
| 数据安全 | 原图、识别文本等数据云同步需加密传输与存储；家长账号需身份验证后才能执行支付、复核申诉等敏感操作 |
| 无障碍 | 正文字号不小于16sp，触控目标不小于44×44dp，遵循 HarmonyOS Design 无障碍规范 |
| 可用性 | 核心录题、复习流程需在弱网环境下可用（本地OCR优先，云端能力降级不阻塞核心流程） |

### 4.1 输入与易用性设计原则（贯穿全部孩子可操作界面）

小学生的打字能力（尤其拼音键盘）普遍弱于点选、语音、手写这几种交互方式，因此凡是孩子需要"表达内容"的地方，都应按以下优先级提供输入方式，优先级越靠前越应作为默认选项：

1. **点选/选择**（按钮、卡片、下拉选择器、候选项）——能选择就不打字，默认首选
2. **拍照/图片**——用镜头替代文字描述（例如讲解笔记直接拍下手写内容，而不是转述打字）
3. **语音输入**（转文字）
4. **手写输入**（手指/触控笔直接书写，系统识别为文字）——小学生对手写的熟悉度通常高于拼音键盘打字，尤其中低年级
5. **键盘打字**——仅作为以上都不适用时的兜底方式，且需提供输入联想/候选词降低击键量

该原则已落实到以下具体功能点，实现时应作为强约束遵循：
- 识别确认修正（FR-OCR-04）
- 讲解笔记（FR-MNG-03）
- 复习作答中的文字类填空题（FR-REV-01）
- 学习档案中的地区/学校字段（FR-PROF-01）
- 错题社区不设自由文本评论区（FR-COM-05）

家长端的操作（如订阅、复核申诉理由）不受此原则约束，可保留常规文字输入，因为家长的打字负担不是本次优化的重点。

### 5.5 跨端演进架构与技术选型

**背景与原则**
当前版本以 HarmonyOS 原生（ArkTS/ArkUI）为起点。跨端演进的核心目标不是"一套代码跑所有平台"，而是保证：① 核心算法与业务逻辑在所有平台上行为一致（尤其是掌握判定、间隔重复排期这类直接影响学习效果的逻辑，不能出现"同一题在手机上判定已掌握、在平板上没判定"的不一致）；② 不同平台的核心使用场景本身不同，允许功能优先级分平台裁剪，而不强行让所有平台功能对齐。

**关键架构决策：把核心逻辑"服务端化"，而不是在每个客户端重复实现**
建议把间隔重复算法（6.3）、自动掌握判定算法（6.4）、社区数据可信度算法（6.5）等这类"结果必须跨端一致"的逻辑，实现为**后端统一服务**，各端通过统一API调用，而不是分别在 HarmonyOS / Android / iOS / Windows 客户端各写一份。
- 好处：算法迭代只需改一处；避免多端实现不一致导致判定结果分裂；便于运营后台（3.12节）直接复用同一套计算结果做统计
- 代价：核心操作（如复习判分）需要联网才能得到最终确认状态，需要设计合理的"离线本地乐观计算 + 联网后与服务端同步校正"机制——客户端可以先用本地缓存的规则给出即时UI反馈，但以服务端返回结果为最终准

**表现层跨端技术方案对比**

| 方案 | 覆盖平台 | 优点 | 缺点/风险 | 适用场景建议 |
|---|---|---|---|---|
| 鸿蒙原生 ArkTS/ArkUI（当前方案） | HarmonyOS | 官方一等公民，性能与系统能力（相机、通知、分布式）支持最完整 | 仅覆盖鸿蒙生态 | 保持作为鸿蒙侧的长期主力方案 |
| 华为 ArkUI-X | 官方方向上覆盖 HarmonyOS + Android + iOS | 复用现有 ArkTS 代码与团队技能，迁移成本相对小 | 对 Windows/macOS 桌面的支持程度、生态成熟度需在开发前查阅最新官方资料核实，不确定性较高 | 若希望最大化复用现有鸿蒙代码资产，优先评估此方案覆盖移动端（Android/iOS）的可行性 |
| Flutter | Android/iOS/Windows/macOS/Linux/Web（鸿蒙侧有第三方 OpenHarmony 适配，非官方主线，需自行验证成熟度） | 一套代码多端覆盖最广，自绘引擎UI一致性高，生态成熟，性能可接受 | 与鸿蒙官方技术栈是两套体系，若鸿蒙侧也想统一到Flutter需额外验证第三方适配的稳定性 | 若计划以 Android/iOS/Windows/macOS 为主战场、鸿蒙保持原生独立维护，是当前较成熟稳妥的多端覆盖方案 |
| React Native | Android/iOS 成熟，Windows/macOS 需额外的 RN Windows/macOS 支持，鸿蒙侧有第三方社区适配 | 生态庞大，Web前端团队复用能力强 | 桌面端与鸿蒙支持均非官方一线，长期维护成本需评估 | 若团队已有较强 React/RN 技术积累，可考虑 |
| Kotlin Multiplatform（KMP） | 用于共享非UI的业务逻辑代码（各端UI仍需原生实现） | 逻辑层一次编写多端复用，原生UI体验最佳 | UI层仍需每端原生开发，跨端覆盖程度低于Flutter/RN | 若核心算法已服务端化（见上），KMP的必要性会降低；如仍需端侧离线计算逻辑，KMP适合替代"多端各写一份算法"的方案 |
| 纯 Web/PWA | 所有带浏览器的平台 | 开发成本最低，跨端覆盖最广 | 拍照/相机等硬件能力体验通常弱于原生App，不适合孩子端核心的拍照识别体验 | 适合作为**桌面端家长/管理后台**的技术方案，不建议作为孩子端主App方案 |

**推荐的分场景架构**

| 使用场景 | 建议技术方案 | 理由 |
|---|---|---|
| 手机/平板（孩子为主，含拍照录题、复习） | 鸿蒙原生 ArkUI（已有）+ 视团队资源决定 Android/iOS 走 ArkUI-X 还是 Flutter | 拍照识别、相机、通知等硬件能力交互体验要求高，优先保证原生或接近原生的体验 |
| Windows/macOS 桌面（家长/教师管理、查看报告、批量导入导出、订阅购买） | Web应用（可选打包为Electron/Tauri桌面壳）或 Flutter Desktop | 桌面场景核心诉求是"管理与查看"而非"拍照录入"，对硬件能力依赖低，Web方案开发成本最低且天然契合"随时随地管理"的使用心智 |
| 内部运营后台（3.12节） | Web BI 应用（成熟Web前端框架 + 现成BI组件/工具） | 与C端技术栈无关，选型自由度最高，优先选熟悉度高、生态成熟的方案 |

**平台差异需要抽象的能力**
- **推送通知**：HarmonyOS Push Kit / iOS APNs / Android FCM（或国内环境下的厂商推送联盟）/ Windows·macOS 系统通知机制各不相同，需要后端封装统一的"推送网关服务"，业务代码只调用统一接口，由网关按目标平台路由到对应推送通道
- **相机/拍照能力**：HarmonyOS Camera Kit / iOS AVFoundation / Android CameraX，桌面端通常无摄像头或使用场景很少，桌面端应以"拖拽/选择本地图片上传"替代拍照，与"支持相册选取已有照片"的设计天然契合，只是桌面端进一步弱化拍照、强化文件上传
- **文字识别（OCR）**：HarmonyOS Core Vision Kit 是鸿蒙专属能力，扩展到其他平台时需评估是否统一改为**云端OCR服务**——所有平台调用同一套云端识别能力，效果和逻辑跨端一致，也避免每个平台单独接入一套不同端侧OCR SDK导致准确率、体验不一致。建议：跨端阶段，OCR核心识别整体收到云端统一处理，端侧只保留"拍照质量前置检测"这类轻量本地能力（多数平台都有对应图像处理库可实现）
- **手写输入识别**（对应4.1节低输入原则）：各平台手写转文字能力成熟度不同，需要逐平台确认可用方案，必要时同样收敛到云端统一服务

**关于是否现在就做跨端的建议**
不建议在产品尚未通过 HarmonyOS 单端验证（留存、复习完成率、掌握判定准确性等核心指标）之前就同步启动多端开发——跨端会显著增加维护成本和一致性风险。建议按"先在单端把核心算法与数据模型跑通、验证有效，再横向复制到其他平台"的顺序推进，这也是本节把"核心逻辑服务端化"作为关键决策的原因：只要服务端先行稳定，后续增加任意一个新客户端平台的边际成本会显著降低。

## 6. 核心算法规格

### 6.1 拍照质量检测（规则示例，具体阈值需实测校准）
```
输入：图像
检测项：清晰度（拉普拉斯方差等常见模糊检测方法）、倾斜角、光照均匀度
输出：PASS 或 { FAIL, reason: BLUR|TILT|GLARE|LOW_LIGHT }
FAIL 时提示对应文案，允许重拍/换图
```

### 6.2 识别与置信度分层策略
```
IF 内容类型 == 印刷体文字:
    使用通用OCR引擎 → 返回 text + confidence
ELSE IF 内容类型 == 数学公式/图形:
    使用专门公式识别引擎 → 返回 text(可含结构化表达) + confidence
IF confidence < CONFIDENCE_THRESHOLD (默认建议 0.85，需实测校准):
    UI 高亮标记该字段，要求用户重点核对
    修正方式按 4.1 节优先级提供：候选词点选 > 语音 > 手写 > 键盘打字
    IF 内容类型 == 手写 AND 已接入多模态大模型兜底:
        触发第二意见识别，结果同样进入强制核对流程，不自动采信
```

### 6.3 间隔重复排期算法
```
INTERVALS_DAYS = [1, 3, 7, 15, 30]   // 可配置

function scheduleNextReview(mistake, reviewResult):
    idx = mistake.interval_index      // 当前所处间隔级别，初始0
    if reviewResult.correct:
        idx = min(idx + 1, len(INTERVALS_DAYS) - 1)
    else:
        idx = 0                        // 答错，回到最短间隔
    mistake.interval_index = idx
    mistake.next_review_date = today() + INTERVALS_DAYS[idx] 天
    return mistake
```

### 6.4 自动掌握判定算法
```
MASTERY_MIN_CONSECUTIVE_CORRECT = 2      // 客观题；主观题建议+1（见下方说明），均可配置
MASTERY_SPEED_RATIO = 0.6                // 用时需低于基准用时的60%，可配置
MIN_DISTINCT_CALENDAR_DAYS = 2           // 判定所需的最近N次复习必须分属不同自然日

function evaluateMastery(mistake):
    logs = mistake.review_logs 按 review_time 降序排列
    required_n = MASTERY_MIN_CONSECUTIVE_CORRECT
    if mistake.grading_method_of_latest == "subjective_selfreport":
        required_n = required_n + 1      // 主观题自评可靠性较低，提高判定门槛

    if len(logs) < required_n:
        return "NOT_MASTERED"

    recent = logs[0 : required_n]

    // 条件1：最近 required_n 次全部正确
    if not all(log.correct for log in recent):
        return "NOT_MASTERED"

    // 条件2：分属不同自然日（避免同日反复刷到"记住"的假象）
    distinct_days = set(calendar_date(log.review_time) for log in recent)
    if len(distinct_days) < min(MIN_DISTINCT_CALENDAR_DAYS, required_n):
        return "NOT_MASTERED"

    // 条件3：用时低于阈值
    baseline = mistake.first_review_duration or gradeBenchmarkDuration(mistake)
    threshold = baseline * MASTERY_SPEED_RATIO
    if any(log.duration_seconds > threshold for log in recent):
        return "NOT_MASTERED"

    return "MASTERED"

// 已判定 MASTERED 的题目如在后续综合测验/抽查中答错：
//   status 重置为 "REVIEWING"，interval_index 重置为 0，重新进入排期
```
> 说明：以上三个阈值常量均为初始经验值，MVP阶段可直接使用，第三阶段建议基于真实复习数据做校准。

### 6.5 社区数据可信度阈值算法
```
MIN_SAMPLE_SIZE = 100                    // 单个(年级,学科,知识点)组合的最小加权样本数，可配置
FRESHNESS_HALF_LIFE_DAYS = 180           // 数据新鲜度半衰期，超期样本按指数衰减权重

function getKnowledgePointInsight(grade, subject, knowledgeTag):
    samples = fetchCommunitySamples(grade, subject, knowledgeTag)
    weighted_count = sum(decayWeight(s.submitted_at, FRESHNESS_HALF_LIFE_DAYS) for s in samples)
    if weighted_count < MIN_SAMPLE_SIZE:
        return { status: "INSUFFICIENT_DATA", display_text: "数据积累中" }
    error_rate = weightedErrorRate(samples)
    return { status: "READY", error_rate: error_rate, sample_size: round(weighted_count) }
```

## 9. 关键用户流程

### 流程 A：拍照录入错题
1. P-01 点击拍照录入 → P-02 选择"拍照"或"相册"
2. 质量检测：不合格 → 提示重拍/换图（异常分支，可重复）；合格 → 自动裁边矫正 → P-02a
3. 圈选第1题 → 识别 → P-02b
4. 逐项核对：候选词点选/语音/手写优先，键盘打字兜底；全部通过后可保存，未通过 → 阻塞提示（异常分支）
5. 可继续圈选下一题或结束保存
6. 保存成功 → 自动计算 next_review_date（6.3）→ 正向反馈提示

### 流程 B：日常复习
1. P-01 显示今日待复习数量 → 进入 P-04
2. 逐题作答：按题型使用点选/数字键盘/手写板/语音作答，客观题自动判分，主观题自评
3. 每题写入 ReviewLog → 触发 6.4 掌握判定 → 若判定为MASTERED，status更新，移出常规排期
4. 全部完成 → P-04a 展示结果与积分

### 流程 C：查看报告与订阅
1. P-06 展示免费基础统计
2. 用户点击"深度报告" → 若家长未订阅 → 展示 P-12 分层预览与购买入口
3. 家长身份验证 → 完成购买 → 生成 Report（premium_deep_report）→ 展示完整内容

### 流程 D：数据导出/导入
1. P-09 选择导出范围与格式 → 生成文件 → 分享/保存
2. 或选择导入文件 → 系统解析预览 → 复用 P-02b 识别确认流程 → 确认后合并入错题本

### 流程 E：加入错题社区
1. 家长在 P-08 开启孩子的浏览/分享权限（默认关闭）
2. 孩子在 P-05a 浏览、点赞、收藏、一键加入我的错题本
3. 孩子发起分享 → 系统自动脱敏 → 通知家长确认 → 家长确认后进入审核队列 → 通过后发布

## 11. 商业化：家长端订阅深度报告设计

### 11.1 报告内容分层
**免费层（孩子/家长均可见，无论是否订阅）**
- 个人错题统计、知识点分布、简单Top3薄弱点

**订阅解锁层**
1. **同年级/同地区对比分析**：孩子在各知识点错误率相对于同年级/同地区其他学生的百分位（依赖6.5节的样本量门槛，未达标不展示）
2. **历史趋势曲线**：跨学期/学年的知识点掌握趋势与进步速度可视化
3. **错误深度归因**：结合错误类型（概念/粗心/审题）交叉分析，给出具体、可执行的学习建议，而非仅"错得多"
4. **跨知识点关联提示**：例如某薄弱知识点通常与哪些前置概念理解不足相关联，建议同步巩固方向
5. **阶段复习优先级建议**：基于社区聚合数据+孩子自身薄弱点，提示本阶段值得重点复习的知识点——**命名与宣传需谨慎，定位为"复习优先级建议"，不使用"押题""预测考题"等用语**，避免误导家长产生不合理预期，也规避应试押题类宣传的合规风险
6. 报告支持导出PDF、分享给老师

### 11.2 定价模型建议
- 建议以**订阅制**为主（按学期/按年），教育类消费决策周期通常与学期对齐；辅以**单次报告购买**（如期中/期末阶段单独购买一份深度报告）作为低门槛选项，两种模式并存
- 分层：基础版免费 + 订阅版解锁深度内容
- **本文档不给出具体价格**：K12学情报告类订阅目前没有找到直接可比的公开定价数据，建议实现方在定价前直接调研2-3款功能相近的现有产品的会员定价区间，再结合自身成本与目标转化率决定
- **不建议的做法**：不做限时倒计时促销、"仅剩XX名额"等制造家长焦虑购买的营销话术

### 11.3 数据规模与可信度门槛
- 复用6.5节算法：单个"年级+学科+知识点"组合需达到最小加权样本量（初始建议100，需按实际DAU与贡献率调整）才对外/对家长展示对比结论，未达标显示"数据积累中"
- 覆盖广度：需覆盖主流教材版本与地区分布，避免因教材版本差异导致对比失真
- 数据新鲜度：采用半衰期加权（默认180天），新学期/教材改版后旧数据自动降权
- 报告中展示对比结论时，需同时标注样本量（如"基于XX份同年级样本"），增强透明度与可信度

### 11.4 转化路径设计要点
- 免费报告页（P-06）中，薄弱知识点Top3等基础信息保持免费可见，深度对比/趋势内容做"模糊预览+解锁引导"，而非完全隐藏
- 购买流程必须发生在家长身份验证之后（P-12），孩子账号内任何界面都不应出现价格或购买按钮
- 报告生成后应可离线保存、可导出，避免家长订阅到期后完全失去历史报告的访问权

## 12. 验收标准（关键模块 Definition of Done）

- **拍照录题**：低质量图片必现重拍提示；未完成识别确认无法保存；原图任何情况下都可被完整访问
- **低输入设计**：识别确认页、复习作答页、学习档案设置页在孩子可操作路径中，默认输入方式为点选/语音/手写；标准键盘打字仅作为兜底且有明确独立入口，不作为默认呈现
- **掌握判定**：给定一组模拟复习记录，算法输出结果与6.4节伪代码逻辑一致；客户端无法绕过算法直接写入 status=mastered
- **复习提醒**：next_review_date 计算结果与6.3节间隔序列一致；答错后间隔重置为最短
- **社区分享**：未经家长确认的内容不会进入公开可见状态；分享内容中原始姓名等信息不可见
- **积分**：PointsLog 中不存在任何"充值兑换积分"记录类型；孩子账号所有页面无支付入口
- **订阅**：SubscriptionOrder 只能由 ParentAccount 创建；报告中的对比类结论必须附带样本量说明
- **运营后台**：运营人员默认视图不可检索到具体某孩子的错题原图/文本内容；案例级查询必须留有审计日志（操作人/时间/原因）
- **跨端一致性（进入5.5阶段后适用）**：若上线多端，掌握判定与间隔重复排期结果需服务端统一计算，同一账号在不同客户端上的展示结果必须一致
