## 2. 客户端（手机端）模块设计

### 2.1 分层结构

```
UI层（Page/Component，对应主规格书 P-01~P-12）
   │
用例层（UseCase，如"提交复习结果""拍照录题"，编排下面两层完成一次完整业务动作）
   │
仓储层（Repository，统一数据访问接口，向用例层屏蔽"数据来自本地缓存还是远程API"）
   │        │
本地数据源   远程数据源（APIClient，封装HTTP请求、鉴权头、幂等Key、离线队列）
   │
能力适配层（Capability Adapter：Camera Kit / Core Vision Kit / Notification Kit / 手写输入 Kit 等系统能力的统一封装）
```

> 能力适配层是未来跨端的关键隔离层：UI层、用例层、仓储层的代码逻辑应尽量与平台无关，替换到其他平台（如Android）时，理论上只需重新实现能力适配层与部分UI层，用例层/仓储层可最大程度复用（尤其在核心算法已服务端化的前提下，用例层的业务规则本身就很薄）。

### 2.2 客户端模块清单

| 模块 | 对应FR | 职责 |
|---|---|---|
| CaptureModule | FR-CAP | 拍照/相册取图、质量检测（本地）、裁边矫正、圈选交互 |

| MistakeRepository | FR-MNG | 错题本地缓存 + 与云端Mistake服务同步，提供统一的错题CRUD接口给上层 |
| ReviewModule | FR-REV | 复习清单获取、按题型渲染作答控件、提交复习结果、接收服务端权威判定结果并更新本地展示 |
| ReminderModule | FR-REM | 本地通知调度（配合系统Notification Kit）、接收云端推送 |

### 2.3 关键模块详细设计

**CaptureModule → RecognitionModule 交接**
1. CaptureModule 完成本地质量检测（6.1算法）与圈选，产出图像区域坐标
2. 调用 APIClient 直传图片至对象存储（预签名URL模式，见4.3），获得 `image_id`
3. 交给 RecognitionModule 提交识别任务，异步轮询结果
4. 识别完成后进入确认页交互，用户确认的不仅是题目文本，**还需确认/标注 `standard_answer`（标准答案）与 `answer_type`（题型：choice/numeric/text/subjective）**——这两个字段是 ReviewModule 之后能否自动判分的前提，识别确认页应在题干/答案之外单独有一个"这道题的正确答案是什么"的确认步骤，而不仅是核对OCR文本（这是对主规格书 FR-OCR-03 的补充说明，建议在实现时同步更新主规格书的 Mistake 数据表，见第7节）

**ReviewModule 的本地乐观策略**
- 客户端内置一份简化版的6.3/6.4规则参数（间隔序列、连续正确次数、速度阈值）用于**弱网/离线时的即时UI反馈**（例如提交答案后立刻显示"太棒了，快要掌握了！"这类即时鼓励文案）
- 但该本地计算结果**不是最终结果**，仅用于不阻塞体验；一旦网络可用，SyncEngine 会把该次提交同步到 ReviewSchedulingService，以服务端返回为准静默修正本地状态（差异较大时可给一次轻量提示，如"网络恢复，刚才的复习结果已更新"）

**SyncEngine（横切模块）**
- 维护一个本地"待同步操作队列"（如：ReviewSubmit、CommunityShare、NotesUpload、AnalyticsEvent等），每条操作生成本地 `client_operation_id`（UUID）
- 网络可用时按队列顺序批量提交，服务端以 `client_operation_id` 做幂等去重（详见第5节）
- 提供统一的"同步状态"给UI层展示（如错题详情页可显示"已同步"/"同步中"角标，非强制但建议实现，便于用户感知数据安全性）

### 2.4 本地存储设计（简要）

本地关系型数据库中，核心表结构与云端 Mistake/ReviewLog/PointsLog 等实体基本一致（详见主规格书第7节），额外补充离线同步所需字段：

| 表 | 新增本地字段 | 说明 |
|---|---|---|
| Mistake（本地） | sync_status: enum(synced/pending/conflict) | 标记该条记录相对云端的同步状态 |
| ReviewLog（本地） | client_operation_id | 用于提交时的幂等标识 |
| CommunityPost（本地缓存） | last_synced_at | 社区内容为只读缓存，定期刷新即可，无需复杂冲突处理 |

## 3. 云端模块设计

### 3.1 架构风格建议

**建议 MVP 与第二、三阶段采用"模块化单体"（Modular Monolith），而非一开始就拆分微服务**，理由：
- 团队规模与业务量早期通常不足以支撑微服务的运维复杂度（独立部署、服务发现、分布式事务等）
- 模块化单体只要内部模块边界清晰（见下方模块清单，每个模块对应独立的代码目录、独立的数据表归属、通过内部接口调用而非直接跨模块读表），后续需要独立扩展的模块可以较低成本拆分为独立服务
- **建议优先拆分为独立服务的两个模块**（如果未来出现明显的扩展/隔离需求）：**RecognitionOrchestrator**（因依赖外部OCR/大模型API，延迟与失败模式与其他模块不同，且未来可能需要独立的限流与降级策略）和 **ReviewSchedulingService**（核心算法服务，调用频率高，且是"结果必须端云/跨端一致"的关键路径，独立部署便于单独做灰度发布与算法AB测试）

### 3.2 云端服务模块清单

| 模块 | 职责 | 依赖 |

### 3.3 数据存储组件

| 组件 | 用途 |
|---|---|
| 主数据库（RDBMS） | Student/ParentAccount/Mistake/ReviewLog/KnowledgeTag/KnowledgeProfile/PointsLog/CommunityPost/SubscriptionOrder/Report 等结构化数据（详见主规格书第7节） |
| 对象存储 | 错题原图、脱敏后图片 |
| 消息队列 | 解耦异步任务：识别任务、审核任务、推送任务、埋点写入，避免阻塞主请求链路 |
| 数据仓库/OLAP | 运营后台查询专用，与在线事务库分离，避免运营查询拖慢线上业务性能；AnalyticsEvent 主要落地于此 |

### 3.4 关键服务详细设计

**RecognitionOrchestrator**
- 输入：`image_id` + 圈选区域坐标
- 内部逻辑：按主规格书6.2节分层识别策略路由到印刷体OCR/公式识别/多模态大模型兜底，合并结果与置信度
- 输出：结构化字段（题干、学生作答、标准答案候选、内容类型、逐字段置信度）
- 异步设计：识别任务提交后立即返回 `job_id`，客户端轮询或订阅结果（详见4.3节接口）；耗时较长的公式/大模型识别路径不阻塞客户端主流程

**ReviewSchedulingService**
- 输入：`mistake_id` + 本次复习结果（正确性、用时、判分方式）
- 内部逻辑：写入ReviewLog → 执行6.4掌握判定算法 → 若判定变化则执行6.3排期算法更新next_review_date → 调用PointsService记录本次积分事件
- 输出：判定结果、判定依据（供家长查看）、下次复习时间、本次获得积分
- 这是整个系统里**唯一权威**计算掌握状态与复习排期的地方，任何客户端（现在的HarmonyOS，未来的Android/iOS/Windows/macOS）都必须通过这个服务获得最终结果，不允许任何客户端本地"确认"掌握状态

**CommunityService 状态机**
```
草稿(分享发起) → pending_parent_confirm（等待家长确认，含自动脱敏处理）
              → pending_review（家长已确认，进入审核队列）
              → published（人工/自动审核通过）
              → rejected（审核不通过，通知发起方）
```

## 4. 端云协同接口设计（API）

### 4.1 通用规范

- **协议**：HTTPS REST（如团队更熟悉GraphQL/gRPC可等价替换，本文档用REST描述以保证通用可读性）
- **鉴权**：请求头 `Authorization: Bearer <token>`；`token` 携带 `token_type: student | parent`，服务端按此区分权限范围——**支付、订阅、复核申诉、学校/地区档案修改等敏感操作强制要求 `token_type=parent`**，学生Token不具备这些权限（这是主规格书FR-SUB-01"孩子账号不出现支付入口"的服务端强制保证，不能只靠客户端UI不显示按钮）
- **幂等**：所有写操作建议携带请求头 `Idempotency-Key: <client_operation_id>`，服务端依据该Key去重，防止离线重试导致重复计分/重复生成记录
- **统一响应结构**：
```json
{
  "code": 0,
  "message": "success",
  "data": { }
}
```
错误响应示例：
```json
{
  "code": 40001,
  "message": "图片质量过低，请重新拍摄",
  "data": null
}
```
- **分页**：列表接口统一返回 `{ items: [], page, page_size, total }`

## 5. 离线与同步策略

### 5.1 可离线操作清单
拍照录题（本地暂存待识别）、复习作答提交、讲解笔记上传、学习档案修改。**不可离线**的操作：订阅购买、社区分享的家长确认（涉及支付与内容发布，要求强一致性，需联网即时确认）。

### 5.2 同步协议
1. 客户端每个可离线写操作生成本地 `client_operation_id`，先落地本地DB并标记 `sync_status=pending`
2. SyncEngine 监听网络状态，恢复后按时间顺序批量提交队列中的操作到对应API
3. 服务端所有写接口依据 `Idempotency-Key`（即 `client_operation_id`）做幂等校验：若该Key已处理过，直接返回此前的处理结果，不重复执行副作用（不重复计分、不重复生成记录）
4. 同步成功后，本地记录 `sync_status=synced`，若涉及权威计算结果（如复习判定），以服务端返回覆盖本地乐观结果

### 5.3 冲突处理策略
- 对于"结果由服务端权威计算"的数据（掌握状态、下次复习时间、积分），不存在真正的冲突，服务端结果直接覆盖本地
- 对于"用户可编辑内容"的数据（讲解笔记、学习档案），采用简单的**最后写入优先（Last-Write-Wins）**，以 `client_submitted_at` 时间戳判断；如需更严谨的多设备协同编辑，可在后续版本引入版本号（`version` 字段）做乐观锁校验，MVP阶段不建议引入过多复杂度
